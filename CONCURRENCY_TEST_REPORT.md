# LegalOS — concurrency test report

Generated by `node tests/m1-concurrency.js` (26 checks). Runs against an isolated instance
with the dev bypass **off**, so a real session cookie is the identity for every call —
without that, `devBypassEmail` overrides the cookie and every request silently runs as the
same person, which would make the revocation tests pass for the wrong reason.

## 1. Parallel request intake

| Field | Value |
|---|---|
| Scenario | 40 simultaneous `POST /api/requests`, all claiming the **same** `id` |
| Parallel operations | 40 |
| Expected | every submission stored, every id unique, no lost write |
| Actual | 40/40 → 201; **40 distinct ids**; 40 stored; 0 lost |
| Fix | none needed — `api/requests.js` mints a suffixed id on collision rather than overwriting |
| Result | **PASS** |

Two genuine submissions are deliberately *not* collapsed: an intake endpoint that silently
merged them would lose a real request. The UI double-click lock (a synchronous `useRef`)
prevents the accidental case at source.

## 6. Lockout guards (defect found and fixed)

| Field | Value |
|---|---|
| Scenario | An administrator deactivates their own account |
| Expected | refused — a disabled account is stopped at the identity gate, so the only account that could re-enable it is the one that just went dark |
| Actual (before) | accepted → **permanent lockout**, unrecoverable through the application |
| Fix | `updateUser` refuses self-deactivation, and refuses any change that would leave **zero active administrators** |
| Actual (after) | 400 "You cannot deactivate your own account"; the admin keeps working |
| Result | **FIXED → PASS** |

## Approval and workflow transitions

Covered by `tests/m1-approval*` fixtures in the closure pass and re-verified here: the
approval gate is enforced **in the engine**, not the UI — `advanceRequestStage` checks
approval authority and the value threshold before moving out of `Approval`, so two racing
clients cannot both advance a record past a gate one of them is not entitled to pass.
Transitions are computed from the record's current stage at call time, so a stale client
cannot force a transition from a stage the record has already left.
