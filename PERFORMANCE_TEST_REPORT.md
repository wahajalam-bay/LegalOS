## The bottleneck that was found, and fixed

`GET /api/registers/contracts?limit=5000` is the call the Contracts page makes on every
visit. Before the fix:

| VU | p50 | p95 | RPS | Payload |
|--:|--:|--:|--:|--:|
| 1 | 53ms | 54ms | 18.6 | 327KB |
| 10 | 535ms | 557ms | 18.5 | 327KB |
| 25 | **1,332ms** | 1,346ms | 18.7 | 327KB |
| 50 | **2,667ms** | 2,691ms | 18.7 | 327KB |

Throughput was pinned at ~18.7 RPS regardless of concurrency — the signature of a
CPU-bound serial section, not I/O.

**Root cause.** Two things, both per request:

1. The server re-serialized ~3.3MB of JSON and then **gzipped it synchronously**
   (`zlib.gzipSync`) for every caller. Identical bytes, recomputed each time, on the one
   thread that also has to answer everyone else.
2. The payload carried lineage that no screen reads. `__raw` (the untouched source cells)
   and `__lineage` (file/sheet/row/parser) are **27% of the contracts payload** — steward
   material I added during the data remediation, being shipped to every table render.

**Fix.**

- Register list responses are now **lean**: `__raw` and `__lineage` are withheld unless
  `?lineage=1` is requested. They remain in the cache, and Data Health still reads them
  server-side, so provenance is undiminished.
- Serialized (and gzipped) responses are **cached, keyed on the ingest's `builtAt`
  timestamp** plus the query. A register only changes when a new dataset is promoted, so
  until then the bytes are identical by definition; a rebuild invalidates every key
  automatically because the timestamp is part of it.

After:

| VU | p50 | p95 | RPS | Payload |
|--:|--:|--:|--:|--:|
| 1 | 1ms | 1ms | 1,500 | 270KB |
| 10 | 4ms | 8ms | 2,000 | 270KB |
| 25 | 8ms | 13ms | 2,830 | 270KB |
| 50 | **16ms** | **17ms** | **3,371** | 270KB |

**p50 at 50 concurrent users: 2,667ms → 16ms. Throughput: 18.7 → 3,371 RPS.**

## Things deliberately not changed

- **Litigation register (81KB, 655ms p50 @ 50 VU).** It benefits from the same cache; the
  remaining time is transfer, not computation. Well inside budget.
- **The client still asks for `limit=5000`.** With the response cache this is no longer
  expensive, and paginating the client would change filtering and KPI behaviour that is
  currently computed over the whole set. Noted rather than rewritten.
- **No N+1 found.** Registers are fetched once per family; detail pages and Documents tabs
  read from the already-loaded dataset and issue no per-row request. The Drive tree is not
  re-fetched to render a Documents tab.

## Memory

The harness observed no growth across 4,964 requests. The dataset is held once per
process; the response cache is bounded (cleared wholesale past 40 entries, and every key
carries `builtAt`, so a superseded dataset's entries can never be served and are
collectable after a rebuild).

## Not covered

- Multi-hour soak testing.
- Multi-process / horizontal scaling: the register cache is per-process, so a second
  instance would hold its own copy.
- Load through Cloudflare and nginx (measured against the application origin only).
